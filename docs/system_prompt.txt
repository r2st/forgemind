====================================================
GENERIC LLM GATEWAY RESPONSIBILITIES
====================================================

The Generic LLM Gateway is the centralized AI control plane that sits between
all Hermes agents and every LLM provider (cloud or self-hosted).

ALL agent inference MUST route through the gateway. NO agent may call an LLM
provider directly.

====================================================
ADMIN-CONFIGURABLE LLM MANAGEMENT
====================================================

The Admin Panel provides CRUD for:

1. Provider Registry
- Add/edit/delete cloud or self-hosted providers
- Fields: name, kind (cloud|self_hosted), base_url, api_key, auth_header,
  enabled, metadata
- Encrypted credential storage at rest
- Health probes to validate provider connectivity

2. Model Registry
- Add/edit/delete models from registered providers
- Fields: provider_id, model_name, display_name, context_window, max_output,
  cost_per_input_token, cost_per_output_token,
  capabilities[reasoning,vision,tools], enabled
- Support for arbitrary model additions

3. Agent-to-Model Mapping
- Each agent (Monitoring, RCA, PdM, Reporting, ChatOps, Production Optimization,
  Supervisor) has:
  * primary_model_id
  * fallback_model_ids[] (ordered fallback chain)
  * temperature, max_tokens, reasoning_mode
  * timeout_s, retry_policy

4. Routing Policies
- Global or per-agent routing strategies:
  * cheapest — minimize cost
  * lowest_latency — minimize response time
  * highest_quality — maximize capability
  * local_only — use only self-hosted models
  * gpu_aware — prefer GPU-backed models
  * compliance_aware — respect data residency / security requirements
- Strategy can be set globally or overridden per agent

5. Fallback Configuration
- Define fallback chains for each agent
- On provider error / timeout / rate-limit, walk the fallback list
- Record every fallback event with reason + timestamp

====================================================
PER-AGENT LLM CONFIGURATION
====================================================

The gateway resolves agent → model mapping from:
1. Agent-specific config (highest priority)
2. Default config
3. System defaults (lowest priority)

Example agent config:
{
  "agent_name": "rca-agent",
  "primary_model": "claude-3-5-sonnet-20241022",
  "fallback_models": ["gpt-4o", "llama-3.1-70b-ollama"],
  "temperature": 0.1,
  "max_tokens": 4096,
  "reasoning_mode": true,
  "timeout_s": 90,
  "retry_policy": "exponential_backoff"
}

Agents send requests with an `X-Agent: <agent_name>` header. The gateway
resolves the config and routes to the correct provider + model.

====================================================
LLM ROUTING ENGINE
====================================================

The routing engine:
1. Receives OpenAI-compatible `/v1/chat/completions` requests
2. Reads `X-Agent` header to identify calling agent
3. Resolves agent → model mapping from config
4. Selects provider based on routing strategy
5. Translates request to provider-native format if needed
6. Executes request with retries + fallback
7. Normalizes response to OpenAI-compatible format
8. Records usage metrics (tokens, cost, latency, provider)

Translation layer:
- OpenAI-compatible providers: pass-through (OpenRouter, Groq, Together, vLLM,
  TGI, llama.cpp, Ollama, etc.)
- Anthropic: translate OpenAI Chat Completions → Anthropic Messages API
- Gemini: translate OpenAI Chat Completions → Gemini GenerateContent API
- Bedrock: translate OpenAI Chat Completions → Bedrock InvokeModel API

====================================================
SELF-HOSTED MODEL SUPPORT
====================================================

The gateway supports local / on-premise inference:

1. Ollama Discovery
- Auto-discover running Ollama instances on the network
- Query `/api/tags` to list available models
- One-click register to model registry

2. vLLM / TGI / llama.cpp Server
- Manual registration via Admin Panel
- Test connectivity with `/v1/models` probe
- Support for custom authentication headers

3. GPU-Aware Routing
- Tag models with GPU requirements
- Route to GPU-backed instances when strategy=gpu_aware

4. Fallback to Cloud
- Configure cloud provider as fallback for local models
- On local model failure, automatically failover to cloud

====================================================
LLM OBSERVABILITY
====================================================

The gateway emits Prometheus metrics:
- `llm_tokens_total{agent, model, provider, direction}` — counter
- `llm_latency_seconds{agent, model, provider}` — histogram
- `llm_failures_total{agent, model, provider, reason}` — counter
- `llm_fallback_total{agent, from_model, to_model, reason}` — counter
- `llm_cost_usd_total{agent, model, provider}` — counter

Structured logs (JSON via structlog):
- Every inference call: agent, model, provider, tokens, latency, cost, cached
- Every fallback event: reason, from_model, to_model, timestamp
- Every provider error: status_code, error_message, provider

Trace propagation:
- Accept `traceparent` header (OpenTelemetry)
- Inject into provider requests
- Return `x-llm-trace-id` header

====================================================
LLM GOVERNANCE
====================================================

1. RBAC
- Admin endpoints require JWT with `admin` role
- Read-only endpoints require `user` or `admin` role
- Inference endpoints require valid JWT (any authenticated user)

2. Quotas & Rate Limiting
- Per-agent quotas: max requests/min, max tokens/day
- Per-user quotas: max requests/min, max tokens/day
- Return 429 when exceeded with Retry-After header

3. Audit Log
- Record every inference call:
  * timestamp, agent, user_id, model, provider, tokens, cost, latency,
    request_hash, response_hash
  * Truncated payload (first 500 chars)
- Queryable via Admin Panel with filters (date range, agent, model, user)

4. Encrypted Credential Storage
- All provider API keys stored encrypted at rest (Fernet)
- Encryption key from env var `GATEWAY_SECRET_KEY`
- Keys never logged or returned in API responses (masked display only)

====================================================
LLM GATEWAY API
====================================================

Inference Endpoints (OpenAI-compatible):
- POST /v1/chat/completions
  Headers: Authorization: Bearer <jwt>, X-Agent: <agent_name>
  Body: OpenAI Chat Completions format
  Response: OpenAI Chat Completions format + usage + custom headers

- GET /v1/models
  Lists all enabled models across all providers

Admin Endpoints (all require admin JWT):
- GET/POST/PUT/DELETE /api/v1/admin/llm/providers
- GET/POST/PUT/DELETE /api/v1/admin/llm/models
- GET/PUT /api/v1/admin/llm/agents/{agent_name}/routing
- GET/PUT /api/v1/admin/llm/agents/{agent_name}/fallback
- GET /api/v1/admin/llm/usage (per-agent, per-model, per-provider analytics)
- GET /api/v1/admin/llm/health (provider health checks)
- GET /api/v1/admin/llm/cost (cost monitoring + forecasting)
- GET /api/v1/admin/llm/audit (audit log with filters)

All admin endpoints are proxied through the main api-gateway service.

====================================================
LLM ARCHITECTURE
====================================================

Request flow:

Hermes Agent
    ↓ (POST /v1/chat/completions, X-Agent: rca-agent)
LLM Gateway
    ↓ (resolve agent → model mapping)
Routing Engine
    ↓ (select provider based on strategy)
Translation Layer
    ↓ (translate to provider-native format if needed)
Provider (OpenAI | Anthropic | Gemini | Ollama | vLLM | etc.)
    ↓ (return native response)
Translation Layer
    ↓ (normalize to OpenAI format)
LLM Gateway
    ↓ (record metrics, log, audit)
Hermes Agent
